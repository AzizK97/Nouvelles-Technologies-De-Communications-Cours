1. Introduction et Concepts Fondamentaux

1.1 Qu'est-ce qu'une Architecture Basée sur les Événements ?

Définition : Une architecture basée sur les événements (Event-Driven Architecture - EDA) est un paradigme de conception logicielle où les composants du système communiquent en produisant et en consommant des événements plutôt que par des appels directs synchrones.

Dans une EDA, un événement représente un changement d'état significatif dans le système. Par exemple :

  • "Une commande a été passée"
  • "Un utilisateur s'est inscrit"
  • "Le stock d'un produit est faible"
  • "Un paiement a été validé"

1.2 Concepts Clés

Événement (Event)

Un événement est un message qui décrit quelque chose qui s'est produit dans le passé. Il contient généralement :

  • Type d'événement : Ex: "OrderPlaced", "UserRegistered"
  • Timestamp : Quand l'événement s'est produit
  • Données : Informations contextuelles (ID utilisateur, montant, etc.)
  • Source : Quel service a émis l'événement
// Exemple d'événement JSON { "eventType": "OrderPlaced", "eventId": "evt-12345", "timestamp": "2025-10-14T10:30:00Z", "source": "order-service", "data": { "orderId": "ord-789", "userId": "user-456", "amount": 150.00, "items": [ { "productId": "prod-111", "quantity": 2 } ] } }

Producteur (Producer)

Un composant qui génère et publie des événements quand quelque chose d'important se produit.

Consommateur (Consumer)

Un composant qui écoute et réagit aux événements qui l'intéressent.

Canal d'Événements (Event Channel/Bus)

Le mécanisme de transport qui achemine les événements des producteurs vers les consommateurs.

1.3 Principe de Fonctionnement

┌─────────────┐         ┌──────────────────┐         ┌─────────────┐
│  Producer   │         │   Event Bus      │         │  Consumer 1 │
│  (Service)  │──emit──▶│  (Message Queue) │──route─▶│  (Service)  │
└─────────────┘         │                  │         └─────────────┘
                        │                  │         ┌─────────────┐
                        │                  │──route─▶│  Consumer 2 │
                        └──────────────────┘         │  (Service)  │
                                                     └─────────────┘

Flux:
1. Le Producer détecte un changement d'état
2. Il crée un événement et le publie sur l'Event Bus
3. L'Event Bus distribue l'événement aux Consumers intéressés
4. Chaque Consumer traite l'événement de manière indépendante

1.4 Caractéristiques Principales

Caractéristique Description
Couplage Faible Les producteurs ne connaissent pas les consommateurs (et vice-versa)
Asynchrone Les producteurs n'attendent pas de réponse immédiate
Réactif Les systèmes réagissent aux événements en temps réel
Scalable Facile d'ajouter de nouveaux consommateurs sans modifier le producteur
Résilient La défaillance d'un consommateur n'affecte pas les autres

2.2 Les Composants Détaillés

A. Event Producer (Producteur)

Rôle : Détecte les changements d'état et génère des événements.

// Exemple en Node.js avec EventEmitter class OrderService { constructor(eventBus) { this.eventBus = eventBus; } createOrder(orderData) { // Logique métier const order = this.saveOrder(orderData); // Publier l'événement this.eventBus.publish('OrderPlaced', { orderId: order.id, userId: order.userId, amount: order.amount, timestamp: new Date() }); return order; } }

B. Event Consumer (Consommateur)

Rôle : Écoute et traite les événements pertinents.

// Service d'inventaire qui réagit aux commandes class InventoryService { constructor(eventBus) { // S'abonner à l'événement eventBus.subscribe('OrderPlaced', this.handleOrderPlaced); } handleOrderPlaced(event) { const { orderId, items } = event.data; // Mettre à jour le stock items.forEach(item => { this.decrementStock(item.productId, item.quantity); }); console.log(`Stock updated for order ${orderId}`); } }

C. Event Bus / Message Broker

Rôle : Infrastructure de messagerie qui achemine les événements.

Technologies courantes :

  • Apache Kafka : Haute performance, distribué, persistant
  • RabbitMQ : AMQP, flexible, routage complexe
  • AWS EventBridge : Serverless, intégration AWS
  • Azure Event Hubs : Streaming d'événements à grande échelle
  • Google Pub/Sub : Messagerie asynchrone globale
  • Redis Pub/Sub : Léger, en mémoire

D. Event Store (Optionnel)

Base de données spécialisée qui stocke tous les événements de manière immuable.

Utilisé pour :

  • Event Sourcing
  • Audit et traçabilité
  • Rejeu d'événements
  • Debug et analyse

2.3 Types d'Event Channels

Type Description Cas d'usage
Point-to-Point Un événement → Un seul consommateur Tâches à exécuter une seule fois
Publish-Subscribe Un événement → Plusieurs consommateurs Notifications, broadcasting
Event Streaming Flux continu d'événements Analytics temps réel, monitoring

3. Patterns de Communication

3.1 Event Notification

Le pattern le plus simple : un service notifie qu'un événement s'est produit, avec des données minimales.

📌 Exemple : Notification d'inscription

// Événement de notification simple { "eventType": "UserRegistered", "userId": "user-123", "timestamp": "2025-10-14T10:30:00Z" } // Les consommateurs récupèrent les détails si nécessaire

Avantage : Couplage minimal, événements légers

Inconvénient : Consommateurs doivent faire des appels supplémentaires

3.2 Event-Carried State Transfer

L'événement contient toutes les données nécessaires pour que les consommateurs n'aient pas à faire de requêtes supplémentaires.

📌 Exemple : État complet dans l'événement

{ "eventType": "UserRegistered", "userId": "user-123", "timestamp": "2025-10-14T10:30:00Z", "userData": { "email": "user@example.com", "name": "John Doe", "country": "Tunisia", "subscriptionPlan": "premium" } }

Avantage : Pas de requêtes supplémentaires, autonomie

Inconvénient : Événements plus gros, possible duplication de données

3.3 Event Sourcing

Tous les changements d'état sont stockés comme une séquence d'événements. L'état actuel est reconstruit en rejouant les événements.

État du Compte Bancaire via Event Sourcing:

Events:
1. AccountCreated    { accountId: "acc-001", balance: 0 }
2. MoneyDeposited    { amount: 1000, timestamp: "..." }
3. MoneyWithdrawn    { amount: 200, timestamp: "..." }
4. MoneyDeposited    { amount: 500, timestamp: "..." }

État actuel = Rejeu de tous les événements
Balance finale = 0 + 1000 - 200 + 500 = 1300
Avantages Event Sourcing :
  • Audit trail complet
  • Possibilité de "time travel" (voir l'état à n'importe quel moment)
  • Debug facilité
  • Possibilité de rejouer les événements

3.4 CQRS (Command Query Responsibility Segregation)

Souvent combiné avec Event Sourcing : séparer les opérations de lecture et d'écriture.

┌──────────┐                          ┌────────────┐
│ COMMAND  │  ──write──▶              │ Write Model│
│  (Write) │             Event Store  │ (Domain)   │
└──────────┘                          └────────────┘
                                             │
                                             │ Events
                                             ▼
                                      ┌────────────┐
┌──────────┐                          │ Read Model │
│  QUERY   │  ◀──read──               │ (Projections)
│  (Read)  │            Optimized DB  │            │
└──────────┘                          └────────────┘

3.5 Saga Pattern

Pour gérer les transactions distribuées via une séquence d'événements et de compensations.

📌 Exemple : Saga de Commande

// Scénario: Créer une commande avec paiement et livraison 1. OrderCreated → Success 2. PaymentRequested → Success 3. InventoryReserved → FAIL (stock insuffisant) // Compensation (rollback) 4. PaymentRefunded 5. OrderCancelled // Événements de compensation publiés automatiquement

4. Technologies et Implémentations

4.1 Apache Kafka

Plateforme de streaming distribuée, leader du marché pour l'EDA.

Caractéristiques :

  • Haute performance (millions de messages/sec)
  • Persistance sur disque
  • Réplication et tolérance aux pannes
  • Rétention configurable des messages
  • Partitionnement pour scalabilité horizontale
