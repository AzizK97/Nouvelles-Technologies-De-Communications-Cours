1. Introduction aux Systèmes Distribués

Définition : Un système distribué est un ensemble de composants informatiques autonomes qui apparaissent aux utilisateurs comme un système unique et cohérent. Ces composants communiquent et coordonnent leurs actions en échangeant des messages.

Dans un système distribué, la synchronisation est cruciale pour maintenir la cohérence des données et coordonner les actions entre les différents nœuds. Les défis principaux incluent la latence réseau, les pannes partielles, et les horloges non synchronisées.

Figure 1 : Architecture d'un Système Distribué

2. Types de Synchronisation

2.1 Synchronisation Temporelle

La synchronisation temporelle vise à maintenir une notion cohérente du temps entre les différents nœuds du système. Cela inclut la synchronisation d'horloges physiques et l'utilisation d'horloges logiques.

2.2 Synchronisation de Données

Ce type de synchronisation assure que les copies de données distribuées restent cohérentes. Elle peut être réalisée de manière synchrone ou asynchrone.

Figure 2 : Types de Synchronisation

3. Synchronisation Upstream et Downstream

3.1 Synchronisation Upstream (Montante)

Upstream : La synchronisation upstream (ou montante) fait référence au processus de transfert de données ou de modifications depuis une source locale vers une destination distante ou centrale. C'est un mouvement "vers le haut" dans la hiérarchie des systèmes.

Caractéristiques principales :

  • Initiative de la source : le système local pousse (push) les modifications
  • Propagation proactive des changements
  • Utilisé pour mettre à jour un système central ou maître
  • Latence potentiellement plus faible pour la propagation
Figure 3 : Synchronisation Upstream (Push)

3.2 Synchronisation Downstream (Descendante)

Downstream : La synchronisation downstream (ou descendante) est le processus par lequel un système local récupère (pull) des données ou des modifications depuis une source distante ou centrale. C'est un mouvement "vers le bas" dans la hiérarchie.

Caractéristiques principales :

  • Initiative du client : le système local tire (pull) les modifications
  • Récupération réactive ou périodique
  • Utilisé pour obtenir les dernières mises à jour d'une source autoritaire
  • Meilleur contrôle par le client sur le timing
Figure 4 : Synchronisation Downstream (Pull)

3.3 Synchronisation Bidirectionnelle

Dans de nombreux systèmes modernes, la synchronisation est bidirectionnelle, combinant les approches upstream et downstream pour assurer une cohérence complète des données.

Figure 5 : Synchronisation Bidirectionnelle

4. Mécanismes de Synchronisation

4.1 Synchronisation Basée sur le Temps

📌 Exemple : Cron Jobs

Un système utilise des tâches planifiées (cron) pour synchroniser les données toutes les heures :

0 * * * * /usr/bin/sync-script.sh

Cette approche est simple mais peut entraîner des retards dans la propagation des changements.

4.2 Synchronisation Basée sur les Événements

📌 Exemple : Webhooks

Lorsqu'un changement se produit dans le système A, un webhook notifie immédiatement le système B pour déclencher une synchronisation. Avantage : latence minimale.

4.3 Réplication Maître-Esclave

Figure 6 : Réplication Maître-Esclave

4.4 Réplication Multi-Maître

Dans une architecture multi-maître, plusieurs nœuds peuvent accepter des écritures simultanément. La résolution des conflits devient alors cruciale.

🔑 Points Clés de la Résolution de Conflits :
  • Last Write Wins (LWW) : La dernière modification gagne (basée sur l'horodatage)
  • Version Vectors : Suivi des versions pour détecter les conflits
  • CRDT (Conflict-free Replicated Data Types) : Structures de données qui garantissent la convergence
  • Résolution manuelle : Intervention humaine pour les cas complexes

5. Tableau Comparatif

Critère Upstream (Push) Downstream (Pull)
Initiative Source (système local) Destination (système distant)
Latence Faible (quasi temps réel) Variable (dépend de la fréquence de polling)
Charge serveur Moyenne (reçoit les push) Élevée (répond aux requêtes)
Charge client Élevée (initie les envois) Moyenne (fait des requêtes)
Contrôle Source contrôle le timing Destination contrôle le timing
Bande passante Optimisée (envoi uniquement si changement) Potentiellement gaspillée (polling inutile)
Complexité Moyenne Simple
Cas d'usage Git push, notifications, webhooks Git pull, RSS feeds, synchronisation périodique

⚠️ Attention : Le choix entre upstream et downstream dépend fortement du contexte. Considérez la fréquence des changements, les exigences de latence, et les contraintes de ressources avant de choisir.

6. Exemples Pratiques

6.1 Git : Un Exemple Classique

📌 Exemple : Workflow Git

Upstream (Push) :

git push origin main

Le développeur envoie ses modifications locales vers le dépôt distant (GitHub, GitLab, etc.).

Downstream (Pull) :

git pull origin main

Le développeur récupère les dernières modifications du dépôt distant vers son environnement local.

6.2 Base de Données Distribuée

📌 Exemple : Cassandra (Multi-Maître)

Apache Cassandra utilise une approche de réplication multi-maître où chaque nœud peut accepter des écritures. La synchronisation se fait de manière bidirectionnelle :

  • Upstream : Un nœud propage ses écritures vers les autres répliques
  • Downstream : Les nœuds demandent les données manquantes via des mécanismes de réparation
  • Résolution de conflits : Utilisation de timestamps (LWW)

6.3 Synchronisation Mobile

📌 Exemple : Application Mobile avec Cloud

Scénario : Une application de notes (comme Evernote ou Notion)

Upstream :

  • L'utilisateur crée une note sur son smartphone
  • L'application pousse immédiatement la note vers le cloud
  • Mécanisme : WebSocket ou API REST POST

Downstream :

  • L'application vérifie régulièrement les nouvelles notes du cloud
  • Polling périodique ou notifications push
  • Synchronisation complète au démarrage de l'application

6.4 E-commerce : Gestion des Stocks

Figure 7 : Synchronisation des Stocks E-commerce

📌 Détails du Scénario

Synchronisation Upstream :

  • Chaque point de vente envoie les transactions en temps réel
  • Le système central met à jour l'inventaire global
  • Prévient les surventes grâce à la mise à jour immédiate

Synchronisation Downstream :

  • Les points de vente reçoivent les mises à jour du stock global
  • Permettent d'afficher la disponibilité en temps réel
  • Synchronisation périodique pour les correctifs d'inventaire

6.5 IoT : Capteurs et Cloud

📌 Exemple : Réseau de Capteurs Météo

Upstream :

  • Capteurs de température envoyent des mesures toutes les 5 minutes
  • Protocole : MQTT avec QoS 1 (au moins une livraison)
  • Données agrégées dans une base de données time-series

Downstream :

  • Capteurs récupèrent les configurations mises à jour
  • Mise à jour du firmware à distance
  • Réception de seuils d'alerte ajustés

7. Cas d'Étude : Plateforme de Réservation Hôtelière Distribuée

📖 Contexte du Cas d'Étude :

La société HotelBooking exploite une plateforme de réservation en ligne présente dans 5 régions du monde (Europe, Amérique du Nord, Amérique du Sud, Asie, Afrique). Chaque région dispose d'un centre de données autonome avec sa propre base de données. Les clients peuvent réserver des chambres d'hôtel partout dans le monde depuis n'importe quelle région.

Architecture actuelle :

  • 5 centres de données régionaux (DC-EU, DC-NA, DC-SA, DC-AS, DC-AF)
  • Chaque DC gère ~2000 hôtels dans sa région
  • Base de données PostgreSQL par région
  • ~100 000 réservations par jour au total
  • Temps de latence inter-régions : 150-300ms
Figure 8 : Architecture Système HotelBooking

7.1 Problématiques Identifiées

⚠️ Problèmes Actuels :
  • Survente : Des chambres sont parfois réservées deux fois simultanément depuis différentes régions
  • Incohérence des prix : Les prix promotionnels ne se propagent pas assez rapidement
  • Disponibilité incorrecte : Un client voit des chambres disponibles qui sont déjà réservées
  • Latence élevée : Les recherches inter-régionales sont lentes

7.2 Questions du TD

❓ Question 1 : Analyse de l'Architecture Actuelle

Énoncé :

Identifiez le type de synchronisation actuellement utilisé par HotelBooking. S'agit-il d'une approche upstream, downstream, ou les deux ? Justifiez votre réponse en analysant les flux de données.

✅ Réponse :

L'architecture actuelle semble utiliser une synchronisation hybride faible ou inexistante, ce qui explique les problèmes rencontrés :

  • Absence de synchronisation upstream efficace : Lorsqu'une réservation est effectuée dans DC-EU, cette information n'est pas immédiatement poussée (push) vers les autres centres de données. Cela explique les surventes.
  • Synchronisation downstream insuffisante : Les centres de données ne récupèrent pas régulièrement (pull) les mises à jour des autres régions, ou le font avec une fréquence trop faible.
  • Architecture en silos : Chaque DC fonctionne de manière autonome, ce qui crée des îlots de données non synchronisés.

Conséquence : Le système présente une cohérence éventuelle très lente, voire aucune cohérence garantie entre les régions.

❓ Question 2 : Proposition de Solution Upstream

Énoncé :

Proposez une solution basée sur la synchronisation upstream pour résoudre le problème de survente. Décrivez le flux de données, le protocole à utiliser, et les composants nécessaires.

✅ Réponse :

Solution : Système de Notification en Temps Réel avec Message Queue

Architecture proposée :

  • Message Broker Central : Apache Kafka ou RabbitMQ déployé dans chaque région avec réplication inter-régionale
  • Topics dédiés :
    • reservations.created
    • reservations.cancelled
    • availability.updated

Flux de données (Upstream) :

  1. Client effectue une réservation dans DC-EU (Hôtel ID=1234, Chambre=101)
  2. DC-EU écrit la transaction dans sa BD locale (cohérence locale immédiate)
  3. DC-EU PUSH un message vers Kafka : {
      "event": "reservation.created",
      "hotel_id": 1234,
      "room_id": 101,
      "timestamp": "2025-10-28T14:30:00Z",
      "source_dc": "EU"
    }
  4. Kafka réplique ce message vers tous les centres de données (latence ~300ms)
  5. Chaque DC consomme le message et met à jour sa BD locale
  6. Disponibilité synchronisée en moins de 500ms

Avantages :

  • Propagation rapide des changements (quasi temps réel)
  • Découplage entre les systèmes
  • Garantie de livraison avec Kafka (persistance)
  • Évolutivité horizontale

Gestion des conflits :

  • Utilisation de timestamps vectoriels pour détecter les réservations concurrentes
  • Règle : "First Write Wins" - la première réservation horodatée l'emporte
  • Compensation automatique si conflit détecté (remboursement + notification)
Figure 9 : Solution Upstream avec Kafka

❓ Question 3 : Stratégie Downstream Complémentaire

Énoncé :

La solution upstream ne suffit pas toujours (pannes réseau, perte de messages). Proposez une stratégie downstream complémentaire pour garantir la cohérence à long terme. Quelle fréquence de synchronisation recommandez-vous ?

✅ Réponse :

Solution : Synchronisation Downstream Multi-niveaux

1. Synchronisation Incrémentale (Pull court terme)

  • Fréquence : Toutes les 5 minutes
  • Mécanisme : Chaque DC interroge les autres DCs pour récupérer les changements depuis le dernier timestamp connu
  • Requête SQL : SELECT * FROM reservations
    WHERE updated_at > '2025-10-28 14:25:00'
    AND source_dc != 'EU'
  • Objectif : Rattraper les messages Kafka manqués

2. Synchronisation Complète (Pull long terme)

  • Fréquence : Une fois par jour (heures creuses, ex: 3h du matin heure locale)
  • Mécanisme : Comparaison complète des checksums par table
  • Processus :
    1. Calcul du checksum de chaque table (MD5 des IDs triés)
    2. Comparaison entre DCs
    3. Si différence détectée → synchronisation complète de la table
    4. Rapport de réconciliation envoyé aux administrateurs
  • Objectif : Garantir la cohérence forte à long terme

3. Synchronisation à la Demande (Pull réactif)

  • Déclencheur : Lorsqu'un utilisateur consulte un hôtel
  • Mécanisme : Requête temps réel vers le DC source pour vérifier la disponibilité
  • Cache : Résultat mis en cache pour 30 secondes
  • Objectif : Garantir la fraîcheur des données affichées à l'utilisateur

Recommandation de Fréquences :

Type Fréquence Latence Acceptable
Incrémentale 5 minutes 5-10 min
Complète 24 heures 24h
À la demande Temps réel < 1s

Avantages de cette approche multi-niveaux :

  • Résilience face aux pannes réseau temporaires
  • Détection et correction automatique des dérives
  • Équilibre entre latence et charge système
  • Cohérence éventuelle garantie (dans les 5 min max)

❓ Question 4 : Gestion des Conflits

Énoncé :

Deux clients (un en Europe, un en Asie) réservent simultanément la même chambre à exactement 14:30:00 UTC. Les deux transactions sont validées localement avant que la synchronisation upstream ne se propage. Comment résoudre ce conflit ? Proposez au moins deux stratégies différentes avec leurs avantages et inconvénients.

✅ Réponse :

Stratégie 1 : Last Write Wins avec Timestamp Étendu

  • Principe : La réservation avec le timestamp le plus précis (incluant microsecondes + ID de DC) gagne
  • Format timestamp : 2025-10-28T14:30:00.123456-EU-TXN-789
  • Règle de résolution :
    1. Comparer les microsecondes
    2. Si égales, comparer l'ID du DC (ordre alphabétique)
    3. Si égales, comparer l'ID de transaction
  • Action : La réservation perdante est automatiquement annulée
  • Compensation :
    • Email d'excuse au client perdant
    • Proposition de chambres similaires
    • Bon de réduction de 10% sur la prochaine réservation

✅ Avantages : Simple, déterministe, automatique

❌ Inconvénients : Mauvaise expérience utilisateur pour le client perdant, arbitraire

Stratégie 2 : Réservation Provisoire avec Confirmation

  • Principe : Introduire un état intermédiaire "PENDING_CONFIRMATION"
  • Flux :
    1. Client effectue réservation → État = PENDING (verrou léger)
    2. Système vérifie dans les 2 secondes si conflit existe
    3. Si pas de conflit → État = CONFIRMED
    4. Si conflit détecté → Les deux passent en état = CONFLICT
    5. Système applique règle de priorité :
      • Client avec programme de fidélité supérieur gagne
      • Ou client qui a le plus de réservations historiques
      • Ou aléatoire si égalité
  • Notification : Le client perdant reçoit notification dans les 3 secondes

✅ Avantages : Plus juste (basé sur la fidélité), fenêtre de détection courte

❌ Inconvénients : Complexité accrue, latence de 2 secondes pour confirmation

Stratégie 3 : Surréservation Contrôlée (Overbooking)

  • Principe : Accepter les deux réservations et gérer le surplus
  • Condition : Activé uniquement si l'hôtel a des chambres de catégorie supérieure disponibles
  • Action :
    1. Les deux réservations sont confirmées
    2. Système alloue automatiquement une chambre supérieure à l'un des clients (upgrade gratuit)
    3. Notification positive : "Félicitations, vous avez été upgradé!"
  • Coût : Perte de revenus sur la chambre supérieure

✅ Avantages : Excellente expérience client, pas d'annulation

❌ Inconvénients : Coût financier, nécessite disponibilité de chambres supérieures

Recommandation :

Utiliser une combinaison des stratégies 2 et 3 :

  • Par défaut : Stratégie 2 (Réservation provisoire)
  • Si conflit + upgrade disponible : Stratégie 3 (Overbooking)
  • Sinon : Stratégie 1 comme fallback (LWW)

8. Conclusion

La synchronisation dans les systèmes distribués est un domaine complexe mais essentiel pour garantir la cohérence et la disponibilité des données. Les approches upstream et downstream représentent deux paradigmes fondamentaux qui peuvent être combinés pour créer des systèmes robustes et efficaces.

🎯 Points Essentiels à Retenir :
  • Upstream (Push) : Idéal pour les mises à jour en temps réel et la propagation rapide des changements
  • Downstream (Pull) : Offre plus de contrôle au client et est plus simple à implémenter
  • Synchronisation bidirectionnelle : Souvent nécessaire dans les systèmes modernes pour une cohérence complète
  • Résolution de conflits : Crucial dans les architectures multi-maître
  • Trade-offs : Chaque approche a ses avantages et inconvénients selon le contexte
Recommandations pour la Conception :

Lors de la conception d'un système distribué, considérez les facteurs suivants :

  • La fréquence des changements de données
  • Les exigences de latence et de cohérence
  • Les contraintes de bande passante et de ressources
  • La tolérance aux pannes et la reprise après incident
  • La complexité opérationnelle acceptable

La maîtrise de ces concepts de synchronisation permet de concevoir des systèmes distribués performants, fiables et évolutifs, capables de répondre aux exigences des applications modernes.
